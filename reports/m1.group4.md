### CI/CD

**Components:**
1. Jenkins Server (Amazon Linux): Jenkins automates the CI/CD process. It pulls code from GitHub, builds Docker images, pushes them to AWS Elastic Container Registry (ECR), and deploys the images to the application server.
1. Application Server (Ubuntu EC2 instance): Hosts both MySQL (running natively, not in a container) and the backend and frontend (running as Docker containers). The frontend and backend containers communicate with each other via Docker's internal network.
1. Amazon ECR (Elastic Container Registry): Stores Docker images built by Jenkins for both backend and frontend.


CI/CD pipeline has been set up to automate the process of building, pushing, and deploying Docker images for both the backend and frontend components of the application. The pipeline is managed using Jenkins with the goal of simplifying the deployment process. <br>

The backend pipeline is designed to pull the latest code from the GitHub repository when triggered. Jenkins retrieves the code from the /server directory, builds the Docker image for the backend and pushes this image to Amazon ECR. Once the image is stored in ECR, Jenkins establishes an SSH connection to the application server and it pulls the new backend image, stops any existing backend container, removes it and runs the new image as a container. The backend container is exposed on port 8000 and it communicates with the database and frontend through Docker's internal networking.


For the frontend, the pipeline is similar but with a slight variation. The frontend code is located in the /client directory of the repository. Jenkins pulls the latest frontend code from GitHub, builds the Docker image on the Jenkins server and pushes the built image to Amazon ECR. After this, Jenkins SSH into the application server, pulls the latest frontend image from ECR and runs it as a Docker container, exposing port 5173. This allows the frontend to communicate with the backend container through the configured API URL.
Separate Pipelines: This approach optimizes resources and avoids unnecessary rebuilding or redeployment.

## Lessons Learned
* Frequent meetings and creating meeting notes for each provide a better sight for all the team members.
* Using the task board efficiently increases transparency and makes task distribution easy.
* Sharing our expertise with the team increases engagement and propagates individual knowledge among the team.
* Late mobile deployment for the PWA application is risky and it creates a great amount of stress on the team members who are responsible for the mobile deployment.
* The lack of a project manager creates an over-democratized team and from time to time it makes decision-making difficult.

The current software is a refined version of the application previously submitted for SWE573. It features a flexible architecture designed to accommodate both desktop and mobile platforms, including a Progressive Web App (PWA) option. The application follows a client-server model, with data stored in a MySQL database on the same server.
